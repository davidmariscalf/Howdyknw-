# Auditoría técnica — Howdyknw · 9 de noviembre de 2026

## Objetivo y evidencia

Se revisaron servidor Node.js/WSS, fuente web/WebRTC/PCM, reproductor, Android TV, Samsung/Tizen y scripts Python de análisis de tráfico. Los cambios se realizaron sobre la rama principal del repositorio. Las pruebas automáticas solo validan la lógica y compilación de estos componentes; **no representan una prueba física de micrófono en una TV**.

## Correcciones implementadas

| Área | Riesgo detectado | Corrección |
|---|---|---|
| Sesiones remotas | Un socket caído podía retener una sala y bloquear la reconexión | Ping/pong periódico y liberación de sockets sin respuesta |
| WebSocket | Un navegador abierto desde otra web podía iniciar conexiones con origen ajeno | Comprobación de origen HTTP(S) del navegador frente al host esperado; los clientes nativos no envían un origen web ordinario |
| Servidor HTTP | Cabeceras de aislamiento incompletas | Política CSP, X-Frame-Options, nosniff y Referrer-Policy |
| Samsung/Tizen | Petición /api/config entre orígenes podía fallar por CORS | Configuración ICE en el mensaje de unión, enviada antes de negociar |
| Samsung/Tizen | Candidatos ICE entrantes antes de la respuesta remota se descartaban | Cola de candidatos hasta instalar remoteDescription |
| Audio PCM | Sin oyentes, las fuentes seguían enviando PCM al servidor | Fuentes web y Android no envían muestras con contador de oyentes cero |
| Audio móvil | AudioContext se activaba demasiado tarde tras varias operaciones asíncronas | Preinicialización en el clic del usuario en modo retransmisión PCM |
| Audio PCM | Volumen PCM no regulable | Control de ganancia en Web Audio, sincronizado con volumen HTMLAudio |
| Operación | No se distinguían claramente conexiones a la sala de muestras recibidas | Contador de receptores, tramas PCM y estado de conexión |
| Invitación | Había que activar el micrófono antes de copiar enlace | Enlace disponible antes de iniciar captura |
| Privacidad | Código de sala en query URL visible para el proxy | Enlace con fragmento #room, con compatibilidad de lectura de enlaces antiguos |
| Capturas TShark | Monitor acumulaba todos los tiempos | Solo mantiene primera y última marca de tiempo |
| Capturas PCAP | Analizador cargaba todo stdout y tiempos en memoria | Procesamiento incremental de filas y ventana de timestamps |
| Interfaz | Cambios UI podían dejar controles JS apuntando a IDs inexistentes | Pruebas automáticas de IDs únicos, referencias y scripts presentes |
| Diagnóstico | Era difícil saber si funcionaba HTTPS/WSS desde el receptor | Botón de prueba HTTP y WebSocket; no activa el micrófono |

## Pruebas implementadas

- Node.js: enlace y señales WebSocket, no envío entre salas, PCM válido, límite de espectadores, rechazo de origen web ajeno, recuperación de sockets muertos, recepción de texto y control de permisos de modo remoto.
- JavaScript: conversión PCM a 16 kHz/PCM16, frame de 20 ms, bloqueo de salida con cero oyentes, validación UI y decodificación.
- Python: metadatos de IPv4/IPv6, DNS AAAA, análisis progresivo, marcas de tiempo finitas, PCAP vacío y rango fijo de memoria.
- Android: compilación automatizada de la APK de depuración.
- Samsung: comprobación sintáctica. No existe aún una prueba en un modelo Tizen concreto ni WGT firmado.

Para verificar la rama:

~~~sh
npm install
npm run check
npm test
python -m unittest -v
~~~

Para el APK Android se utiliza la automatización de GitHub Actions `Android TV build`.

## Limitaciones y tareas que requieren pruebas fuera del repositorio

1. **Físicas:** no se ha verificado el acceso a audio de ningún micrófono real de LG, Samsung o Android TV. Si el firmware lo bloquea, la app no puede recuperarlo y el teclado solo proporciona transcripción.
2. **Acceso remoto:** Railway ha rechazado la creación del proyecto por período de prueba caducado; no se ha desplegado ningún servicio público estable. Es necesario habilitar facturación o iniciar `npm run remote` y configurar Tailscale Funnel desde un equipo propio.
3. **Privacidad criptográfica:** PCM/WSS 1.3 dispone de AES-256-GCM extremo a extremo y el servidor remoto rechaza PCM sin cifrar. El servidor no recibe el secreto, pero un hosting comprometido puede modificar el JavaScript que sirve al receptor. Falta auditoría criptográfica externa.
4. **Autenticación:** la sala utiliza un código compartido para entrar, y PCM 1.3 usa además una clave E2EE independiente para descifrar. No hay cuentas ni validación de identidad del emisor; evita publicar claves o enlaces de invitación, usa claves aleatorias largas y rótalas.
5. **Resiliencia de producción:** las salas viven en memoria de un solo proceso; no hay replicación de estado ni persistencia. Reiniciar el servidor termina las sesiones.
6. **Rendimiento:** la retransmisión PCM es sin compresión y el servidor puede consumir ancho de banda proporcional al número de receptores. La UI y la red determinan la latencia real.
7. **Pruebas reales:** no hay pruebas físicas de conexiones a través de dos ISP, audio real en móvil ni certificados/firmas Tizen. Las pruebas de CI no sustituyen esas evidencias.

## Criterio de aceptación para una TV real

Se debe registrar marca/modelo/firmware y versión de APK, confirmar permiso de micrófono y observación visible de su estado, identificar entrada PCM realmente enrutable, conectar receptor desde otra red, observar contador de oyentes y reproducción audible, comprobar que sin oyentes deja de subir PCM, y confirmar la desconexión al pulsar Detener o salir. Registrar solo señales/test audio voluntario, no conversaciones privadas.

## Actualización 1.3: cifrado y empaquetado Samsung

- Android TV 1.3 y el navegador en modo PCM cifran las muestras con AES-256-GCM antes de pasarlas al relay, con clave separada del código de sala. Se han añadido tests de cifrado/tampering/replay y vectores Java/Python de interoperabilidad. Consulta [el protocolo](END_TO_END_ENCRYPTION.md).
- El arranque público del servidor rechaza clientes PCM heredados sin cifrar. Para que funcione en otra red, se necesita desplegar un servidor accesible con HTTPS/WSS.
- Samsung: fuente Tizen empaquetada en ZIP y firma local automatizable mediante `tizen-tv/package-with-profile.sh` **solo si** el propietario dispone de Tizen Studio y certificado Samsung registrado con el DUID del televisor. No hay WGT firmado desde el repositorio ni prueba Samsung física.
- Las pruebas automatizadas de GitHub y el build de Android no sustituyen una prueba de campo entre una televisión y un teléfono en redes distintas.
